PROBLEM STATEMENT
================================================================================

Dairy collection centers manage hundreds of farmers daily, tracking milk 
collection, calculating payments based on quality parameters, managing feed 
purchases, and maintaining financial ledgers. Everything was manual—paper 
ledgers, spreadsheet calculations—leading to errors and payment delays. 
Additionally, farmers needed a way to discover and connect with local equipment 
vendors for purchasing dairy machinery and equipment. There was no centralized 
platform to browse available equipment, compare prices, or contact vendors directly.

My system automates the entire workflow—farmer registration, milk collection, 
rate calculation, feed management, financial ledger, payment settlement, and now 
includes an equipment marketplace where farmers can browse and discover local 
vendors and their equipment offerings. The system ensures accuracy, transparency, 
and efficiency while providing a complete digital ecosystem for dairy operations.


ARCHITECTURE OVERVIEW
================================================================================

The system is a modular Spring Boot monolith. I chose a monolith because the 
modules are tightly coupled through the financial workflow. Milk collection, feed 
purchase, and settlement are interconnected—changes in one affect the others. A 
monolith simplifies transaction management, data consistency, and deployment. The 
backend follows layered architecture: Controllers → Services → Repositories → 
Database. The frontend is React with Vite, communicating via REST APIs.

Technology Stack:

Backend:
- Spring Boot 3.x with Java 17
- Spring Security with JWT authentication
- Spring Data JPA with Hibernate
- PostgreSQL database
- Lombok for reducing boilerplate
- BCrypt for password hashing
- Twilio for SMS OTP

Frontend:
- React 18 with Vite
- React Router for client-side routing
- Axios for API communication
- Tailwind CSS for styling
- React Hot Toast for notifications

1. FARMER MANAGEMENT MODULE
================================================================================

Purpose: Complete CRUD operations for managing dairy farmers with Aadhaar 
verification and bank details.

Features:
- Farmer registration with personal details, Aadhaar number, and bank information
- Farmer activation/deactivation for managing active vs inactive accounts
- Each farmer is linked to an admin for tenant isolation
- Search functionality by name, Aadhaar, or phone
- Pagination for handling large datasets

Technical Implementation:
- Entity: Farmer with one-to-many relationships to MilkCollection, FeedPurchase, 
  and FinancialTransaction
- Repository methods: findByAdminAndActiveOrderByFullNameAsc filters by tenant 
  and status
- DTOs: FarmerRequest and FarmerResponse separate internal entities from API 
  contracts
- Service layer handles business logic and validation
- Controller uses @PreAuthorize for role-based access control

Multi-Tenant Isolation:
- Every farmer record has an admin_id foreign key
- Repository methods always include admin context in queries
- Service layer gets logged-in admin from SecurityContext and passes to 
  repositories
- This ensures each tenant (dairy center) can only access their own farmers

Interview Questions for Farmer Module:

Q: How do you ensure tenant isolation in the Farmer module?
A: Every farmer record has an admin_id foreign key. Repository methods like 
   findByAdminAndActiveOrderByFullNameAsc always filter by admin. The service 
   layer gets the logged-in admin from SecurityContext and passes it to 
   repository methods. This ensures each tenant can only access their own 
   farmers.

Q: How do you handle farmer activation/deactivation?
A: I use an active boolean field in the Farmer entity with default value true. 
   The repository has methods like findByAdminAndActiveOrderByFullNameAsc that 
   filter by active status. Admin can toggle this status via activate/deactivate 
   endpoints. This is a soft delete approach—records remain in database but are 
   filtered out from active queries.

Q: Why did you choose soft delete over hard delete for farmers?
A: Soft delete maintains historical data for audit trails and financial records. 
   If a farmer is deactivated, their past milk collections and financial 
   transactions must remain for reconciliation. Hard delete would break referential 
   integrity with transaction records.


2. MILK COLLECTION MODULE
================================================================================

Purpose: Record daily milk submissions with quality testing and automatic rate 
calculation.

Features:
- Record milk collection with shift tracking (morning/evening)
- Capture quantity, fat percentage, and SNF values
- Automatic price calculation based on configured rate card
- Creates credit entry in financial ledger
- Date-wise collection tracking

Technical Implementation:
- Entity: MilkCollection linked to Farmer and RateCard
- Service applies rate card logic: amount = quantity * rate based on fat/SNF 
  ranges
- Transactional operation: saves collection and creates financial ledger entry 
  atomically
- Repository methods filter by admin, farmer, and date range
- DTOs include calculated amount for API responses

Business Logic:
- Rate card lookup based on fat and SNF values
- Quantity validation (must be positive)
- Shift validation (morning/evening only)
- Automatic ledger credit creation with running balance

Interview Questions for Milk Collection Module:

Q: How does the automatic rate calculation work?
A: When milk collection is recorded, the service looks up the rate card based 
   on fat percentage and SNF values. The rate card defines price per liter for 
   different quality ranges. The amount is calculated as quantity * rate. This 
   incentivizes quality milk production by linking payments to quality parameters.

Q: How do you ensure data consistency between milk collection and financial 
   ledger?
A: I use @Transactional annotation on the service method. The milk collection save 
   and financial ledger creation happen in the same transaction. If either 
   operation fails, the entire transaction rolls back, ensuring data consistency.

Q: How do you handle shift tracking (morning/evening)?
A: The MilkCollection entity has a shift field with values MORNING or EVENING. 
   Frontend provides a dropdown to select shift. Backend validates that only 
   these two values are accepted. This allows tracking of collection patterns 
   and calculating daily totals.


3. RATE & PRICING MANAGEMENT MODULE
================================================================================

Purpose: Dynamic pricing engine supporting different rates based on quality 
parameters.

Features:
- Configure rate cards with fat percentage, SNF, and quantity tiers
- Admin can update rates as market conditions change
- Rates applied automatically during milk collection
- Version history for rate changes

Technical Implementation:
- Entity: RateCard with fat range, SNF range, and rate per liter
- Service provides rate lookup based on quality parameters
- Repository methods find matching rate card for given parameters
- Admin-only access with @PreAuthorize("hasRole('ADMIN')")

Differentiation:
- Incentivizes quality milk production by linking rates to quality parameters
- Flexible pricing allows market-responsive rate adjustments
- Complex business logic beyond simple CRUD

Interview Questions for Rate & Pricing Module:

Q: How does the rate card lookup work?
A: The rate card entity defines fat range (minFat, maxFat), SNF range (minSnf, 
   maxSnf), and rate per liter. When milk collection is recorded, the service 
   queries for a rate card where the fat and SNF values fall within the defined 
   ranges. If multiple rate cards match, it uses the first one or the most 
   specific one.

Q: How do you handle rate changes over time?
A: Rate cards are versioned with effective dates. When looking up rates for milk 
   collection, the service queries for rate cards effective on the collection 
   date. This ensures historical collections use the rates that were applicable 
   at that time, even if rates have changed since then.

Q: Why is this module important beyond simple CRUD?
A: It implements complex business logic—dynamic pricing based on quality 
   parameters. This is not just storing and retrieving data; it's applying rules 
   to calculate payments. This differentiates the system from a typical CRUD 
   application by embedding domain-specific business logic.

Interview Questions for Feed Management Module:

Q: How does feed purchase integrate with the financial ledger?
A: When a farmer purchases feed on credit, the service creates a FeedPurchase

   The running balance in the ledger is updated. This debit is later deducted

Q: How do you handle inventory tracking?
A: The Feed entity tracks current stock quantity. When feed is purchased, the 
   stock is decremented. Admin can add stock when new feed arrives. Low-stock 
   alerts can be implemented by checking if stock falls below a threshold and 
   notifying the admin.

Q: What validation do you apply to feed purchases?
A: Validate that the farmer has sufficient credit balance (optional), that the 
   requested quantity is available in stock, and that the feed item exists and is 
   active. These validations prevent invalid purchases and maintain data 
   integrity.


5. FINANCIAL LEDGER MODULE
================================================================================

Purpose: Core module maintaining running balances for complete audit trail.

Features:
- Records every credit (milk collection) and debit (feed purchase)
- Maintains running balance for each transaction
- Complete audit trail for financial reconciliation
- Farmer-wise statements and period-wise summaries

Technical Implementation:
- Entity: FinancialTransaction with type (CREDIT/DEBIT), amount, and running 
  balance
- Service calculates running balance on each transaction
- Repository methods fetch transactions by farmer and date range
- DTOs include running balance for API responses

Business Logic:
- Running balance calculation: previous balance + credit - debit
- Transactions are ordered chronologically
- Cannot be modified after creation (immutable ledger)
- Settlement marks transactions as settled

Interview Questions for Financial Ledger Module:

Q: How do you calculate running balance?
A: When a new transaction is created, the service fetches the latest transaction 
   for that farmer and gets its running balance. For a credit, new balance = 
   previous balance + amount. For a debit, new balance = previous balance - 
   amount. This running balance is stored with each transaction for quick 
   lookup and audit trail.

Q: Why is the ledger immutable?
A: Financial transactions should never be modified after creation to maintain 
   audit integrity. If an error is discovered, a correcting transaction is 
   created instead of modifying the original. This ensures complete audit trail 
   and prevents tampering with financial records.

Q: How do you handle settlement?
A: Settlement calculates the net payable amount for a farmer over a period by 
   summing credits and debits. It generates a payment voucher and marks the 
   included transactions as settled. This prevents double-payment and provides 
   clear payment history.


6. PAYMENT SETTLEMENT MODULE
================================================================================

Purpose: Process periodic payments to farmers after deducting expenses.

Features:
- Calculate net payable amount after deducting feed purchases
- Generate payment vouchers
- Mark transactions as settled
- Payment history tracking

Technical Implementation:
- Service aggregates credits and debits for a period
- Calculates net payable: total credits - total debits
- Creates Settlement record with transaction references
- Updates FinancialTransaction settled flag
- Repository methods fetch unsettled transactions

Business Logic:
- Only unsettled transactions are included in settlement
- Once settled, transactions cannot be included in another settlement
- Supports partial settlements (settle specific date range)
- Generates printable payment voucher

Interview Questions for Settlement Module:

Q: How do you calculate net payable amount?
A: The service fetches all unsettled financial transactions for a farmer within 
   a date range. It sums all credits (milk collection) and debits (feed 
   purchases). Net payable = total credits - total debits. This is the amount 
   the farmer should receive.

Q: How do you prevent double-payment?
A: Each FinancialTransaction has a settled boolean flag. When a settlement is 
   created, all included transactions are marked as settled. Future settlements 
   only include transactions where settled = false. This prevents the same 
   transaction from being paid multiple times.

Q: What happens if a settlement needs to be reversed?
A: If a settlement error is discovered, a reversal settlement is created with 
   negative amounts. The original transactions' settled flags remain true, but 
   the reversal creates a new credit/debit to correct the balance. This maintains 
   audit trail while correcting errors.

Interview Questions for Vendor Module:

Q: How do you ensure vendor phone numbers are unique per tenant?
A: I have a unique constraint on (admin_id, phone) in the database. Before 
   creating or updating a vendor, the service checks if a vendor with the same 
   phone exists for the same admin using existsByAdminAndPhone method. If it 
   exists, it throws an exception. This ensures no duplicate phone numbers within 
   a tenant while allowing different tenants to have vendors with the same phone.

Q: How do you handle vendor activation/deactivation?
A: The Vendor entity has an active boolean field with default value true. The 
   repository has methods like findByAdminAndActiveOrderByNameAsc that filter 
   by active status. Admin can toggle this status via activate/deactivate PATCH 
   endpoints. When deactivated, the vendor is hidden from farmers but still 
   visible to admin in the "Inactive" tab for reactivation. This is a soft delete 
   approach.

Q: Why did you choose soft delete for vendors instead of hard delete?
A: Soft delete maintains historical data. If a vendor is deactivated, their 
   equipment records and any associated data must remain for audit purposes. Hard 
   delete would break referential integrity with equipment records. Also, vendors 
   might return later, so reactivation is easier than recreating the record.

Q: How do you calculate equipment count for each vendor?
A: In the VendorResponse mapping method, I query the Equipment repository with 
   findByVendorAndActiveOrderByNameAsc(vendor, true) to get all active equipment 
   for that vendor, then call size() on the result list. This count is included 
   in the VendorResponse DTO. It's calculated dynamically to reflect real-time 
   inventory.

Q: How does search functionality work for vendors?
A: The searchByAdmin repository method uses LIKE queries to search by vendor 
   name. If the search query is a number, it first checks for an exact ID match. 
   The frontend implements debounced search (400ms delay) to reduce API calls 
   when the user is typing. The backend accepts a query parameter and returns 
   matching vendors.

Q: How do you ensure multi-tenant isolation for vendors?
A: Every vendor record has an admin_id foreign key. Repository methods like 
   findByAdminOrderByNameAsc always filter by admin. The service layer gets the 
   logged-in admin from SecurityContext and passes it to repository methods. This 
   ensures each tenant (dairy center) can only access their own vendors. Farmers 
   can only see vendors belonging to their admin through the same mechanism.

Interview Questions for Equipment Module:

Q: How do you handle image uploads for equipment?
A: I have a dedicated upload endpoint that accepts MultipartFile. The service 
   validates file size (max 5MB) and type (must be image/*). It generates a 
   unique filename using UUID to avoid conflicts, saves the file to the configured 
   upload directory, and returns the relative URL path. The URL is stored in the 
   equipment's imageUrl field. Images are served via Spring's static resource 
   mapping configured in WebMvcConfig.

Q: How do you ensure uploaded images are secure?
A: I validate file type by checking the MIME type (must start with image/). I 
   limit file size to 5MB to prevent denial of service. I generate random filenames 
   with UUID to prevent path traversal attacks. Images are stored outside the web 
   root and served through a controlled endpoint. In production, I would use cloud 
   storage (S3) with proper access controls.

Q: How do you handle price precision for equipment?
A: Price is stored as BigDecimal with precision 10 and scale 2, which supports 
   values up to 99,999,999.99 with 2 decimal places. BigDecimal is used instead 
   of double to avoid floating-point precision errors. The frontend formats the 
   price with Indian locale (₹ symbol and comma separators) for display.

Q: How does equipment activation/deactivation work?
A: The Equipment entity has an active boolean field with default value true. 
   The repository has methods like findByAdminAndActiveOrderByNameAsc that filter 
   by active status. Admin can toggle this status via activate/deactivate PATCH 
   endpoints. When deactivated, the equipment is hidden from farmers but still 
   visible to admin in the "Inactive" tab for reactivation. This is a soft delete 
   approach.

Q: How do you ensure multi-tenant isolation for equipment?
A: Every equipment record has an admin_id foreign key. Repository methods like 
   findByAdminOrderByNameAsc always filter by admin. The service layer gets the 
   logged-in admin from SecurityContext and passes it to repository methods. This 
   ensures each tenant (dairy center) can only access their own equipment. 
   Farmers can only see equipment belonging to their admin through the same 
   mechanism.

Q: What happens when a vendor is deleted?
A: The Vendor entity has cascade=ALL on the equipmentList relationship. When a 
   vendor is deleted, all associated equipment records are automatically deleted 
   due to cascading delete. This maintains referential integrity. The admin is 
   warned about this before deletion via a confirmation dialog.

Q: How do you handle search functionality for equipment?
A: The searchByAdmin repository method uses LIKE queries to search by equipment 
   name and company name. If the search query is a number, it first checks for an 
   exact ID match. The frontend implements debounced search (400ms delay) to 
   reduce API calls when the user is typing. The backend accepts a query parameter 
   and returns matching equipment.

Q: Why did you use BigDecimal for price instead of double?
A: BigDecimal provides exact decimal arithmetic, while double has floating-point 
   precision errors. For financial calculations like price, accuracy is critical. 
   For example, 0.1 + 0.2 in double gives 0.30000000000000004, but BigDecimal 
   gives exactly 0.3. This prevents calculation errors in pricing.

SECURITY ARCHITECTURE
================================================================================

JWT Authentication:
- Stateless authentication using JWT tokens
- Token contains user ID and role claims
- Custom JWT filter intercepts requests, validates token, sets security context
- Token expiration configured (e.g., 24 hours)
- Refresh token mechanism can be added for better UX

Spring Security Configuration:
- CSRF disabled for stateless API
- CORS enabled for frontend-backend communication
- Public endpoints: login, register, password reset
- Protected endpoints: all other endpoints require authentication
- Role-based access control with @PreAuthorize annotations

Role-Based Access Control:
- Admin role: Full access to all modules
- Farmer role: Limited access to own data and vendor browsing
- @PreAuthorize("hasRole('ADMIN')") on admin-only endpoints
- @PreAuthorize("hasAnyRole('ADMIN', 'FARMER')") on shared endpoints

Password Security:
- BCrypt hashing for password storage
- Never store plain text passwords

Interview Questions for Security:

Q: How does JWT authentication work in your system?
A: When a user logs in with valid credentials, the system generates a JWT token 
   containing user ID and role claims. The token is returned to the client and 
   stored (e.g., in localStorage). For subsequent requests, the client includes 
   the token in the Authorization header (Bearer token). A custom JWT filter 
   intercepts each request, extracts the token, validates it using JwtUtil, and 
   sets the security context with user details and roles.

Q: How do you handle token expiration?
A: JWT tokens have an expiration time configured (e.g., 24 hours). When a token 
   expires, the JWT filter throws an exception, and the frontend receives a 401 
   Unauthorized response. The frontend then redirects the user to the login 
   page. For better UX, I can implement refresh tokens—short-lived access tokens 
   with longer-lived refresh tokens that can obtain new access tokens.

Q: How do you implement role-based access control?
A: I use Spring Security's @PreAuthorize annotations on controller methods. For 
   example, @PreAuthorize("hasRole('ADMIN')") restricts an endpoint to admin users 
   only. The JWT token includes role claims, which are loaded into the security 
   context by the JWT filter. Spring Security evaluates the @PreAuthorize 
   expression against the security context to grant or deny access.

Q: How does the Twilio OTP password reset work?
A: User requests password reset with their phone number. System generates a random 
   6-digit OTP, hashes it, and stores in database with expiration timestamp (15 
   minutes from now). System sends the plain OTP via Twilio SMS API to the user's 
   phone. User enters OTP on the frontend. Backend validates by hashing the input 
   and comparing with stored hash, checking expiration. If valid, user can set 
   new password. OTP is then invalidated.

Q: Why did you choose BCrypt for password hashing?
A: BCrypt is designed specifically for password hashing. It's slow (prevents brute 
   force attacks), includes salt automatically (prevents rainbow table attacks), 
   and is industry-standard. Spring Security provides BCryptPasswordEncoder out 
   of the box. It's more secure than MD5, SHA-1, or SHA-256 for passwords because 
   of its computational cost and built-in salting.

Q: How do you ensure multi-tenant security?
A: Every data record has an admin_id foreign key. Repository methods always include 
   admin context in queries (e.g., findByAdminAndActiveOrderByFullNameAsc). The 
   service layer gets the logged-in admin from SecurityContext and passes it to 
   repositories. For farmers, the service extracts admin from the farmer's 
   security context. This ensures each tenant can only access their own data, and 
   cross-tenant data access is impossible at the database level.

Interview Questions for Database Design:

Q: How did you design the relationships between entities?
A: I followed the real-world domain relationships. Admin has many farmers (one 
   dairy center serves many farmers). Farmer has many milk collections, feed 
   purchases, and financial transactions (ongoing relationship). Vendor has many 
   equipment (one vendor sells multiple products). These are one-to-many 
   relationships implemented with foreign keys. I used JPA's @ManyToOne and 
   @OneToMany annotations to map these relationships.

Q: Why did you add indexes on specific columns?
A: I added indexes on columns frequently used in WHERE clauses and JOINs. For 
   example, admin_id is indexed because every query filters by tenant. farmer_id 
   is indexed because we frequently fetch a farmer's transactions. date is indexed 
   because we often query by date ranges for reports. Indexes speed up these queries 
   significantly, though they slow down inserts/updates slightly.

Q: How do you handle referential integrity?
A: Foreign key constraints enforce referential integrity at the database level. 
   For example, milk_collection has farmer_id foreign key referencing Farmer table. 
   You cannot insert a milk collection without a valid farmer. I use cascading 
   deletes selectively—when a vendor is deleted, associated equipment is also 
   deleted (cascade=ALL). But when a farmer is deleted, their transactions are 
   kept for audit (no cascade).

Q: Why did you choose PostgreSQL over MySQL?
A: PostgreSQL has advanced features like better JSON support, full-text search, 
   and more robust indexing options. It has strong ACID compliance and is 
   open-source. For this project, either would work, but PostgreSQL's advanced 
   features provide more flexibility for future enhancements like complex reporting 
   or JSON data storage.

Q: How do you handle data migration between environments?
A: I use Flyway for database migrations. Versioned SQL scripts are placed in 
   db/migration directory. Flyway tracks which migrations have been applied. On 
   application startup, Flyway runs any pending migrations. This ensures database 
   schema is consistent across development, testing, and production environments.

Intermediate Questions:

Q: How did you implement multi-tenant architecture in your project?

Q: How do you handle exceptions in your Spring Boot application?
A: Global exception handler with @ControllerAdvice. Custom exceptions like

Q: What is optimistic locking and how would you implement it?
A: Optimistic locking assumes conflicts are rare. Uses version field—each update 
   increments version. Before update, check if version matches. If not, throw exception. 
   I implemented it with @Version annotation in JPA entities.

Q: How do you optimize database queries in your project?
A: Indexes on frequently queried columns. Use JOIN FETCH to avoid N+1 queries. Proper 
   entity relationships with lazy loading. Custom JPQL queries for complex operations. 
   Database connection pooling with HikariCP.

Q: What is the N+1 query problem?
A: When fetching N parent records, N additional queries fetch child records. Solved 
   with JOIN FETCH or @EntityGraph.

Q: What is the purpose of the Service layer?
A: Service layer contains business logic. It orchestrates multiple repository calls, 
   applies business rules, handles transactions. Controllers delegate to services, 
   services use repositories. This separation improves testability and maintainability.

Q: How does Spring Data JPA work?
A: Spring Data JPA provides repository interfaces. You define interface extending 
   JpaRepository, Spring provides implementation at runtime. Derived query methods 
   from method names. Custom queries with @Query annotation.

Q: What is a derived query method?
A: Method name describes query— findByAdminAndActiveOrderByFullNameAsc translates 
   to SELECT ... WHERE admin = ? AND active = ? ORDER BY full_name.

Q: What is the difference between lazy and eager loading in JPA?
A: Lazy loading loads related entities when accessed. Eager loading loads immediately 
   with parent. I used lazy loading by default (@ManyToOne(fetch = FetchType.LAZY)) 
   to avoid unnecessary queries. Used JOIN FETCH when needed.

Q: What is the LazyInitializationException?
A: Occurs when accessing lazy-loaded entity outside transaction context. Solved by 
   keeping transaction open or using JOIN FETCH.

Q: How do you handle concurrent updates to the same farmer record?
A: Optimistic locking with @Version field. When two users update simultaneously, the 
   second update fails if version changed. Catch OptimisticLockException and handle 
   gracefully—notify user, retry, or merge changes.

Q: What if you need pessimistic locking?
A: Use @Lock(LockModeType.PESSIMISTIC_WRITE) on repository method. Locks record in 
   database during transaction.

Q: What is the purpose of @EntityGraph in JPA?
A: @EntityGraph defines fetch plan for queries. It specifies which associations to 
   load eagerly, overriding default lazy loading. Used to solve N+1 query problem 
   without JOIN FETCH in every query.

Q: How is it different from JOIN FETCH?
A: @EntityGraph is reusable across queries, defined separately. JOIN FETCH is 
   per-query, embedded in JPQL.

Q: How do you implement audit logging in your application?
A: @CreatedDate, @LastModifiedDate, @CreatedBy, @LastModifiedBy annotations on 
   entities. Enable JPA auditing with @EnableJpaAuditing. Automatically tracks who 
   created/modified records and when.

Q: What if you need custom audit logging?
A: Use EntityListeners with @PrePersist, @PreUpdate callbacks, or AOP aspects to 
   log changes.

Q: What is the difference between @Component, @Service, and @Repository?
A: All are stereotypes for Spring beans. @Component is generic. @Service indicates 
   business logic layer. @Repository indicates data access layer, enables exception 
   translation. Spring scans and registers them as beans.

Q: Why use these annotations instead of @Bean?
A: Auto-scanning reduces configuration, semantic meaning improves code readability,

Q: How do you handle file uploads in your application?

A: @Value for individual properties. @ConfigurationProperties for grouped properties,

A: HikariCP is a JDBC connection pool. Spring Boot uses it by default. It manages

Q: How do you tune HikariCP?

Q: What is the purpose of @Transactional propagation?
A: Propagation defines how transactions relate to each other. REQUIRED (default)

Q: When would you use REQUIRES_NEW?
A: When you need independent transaction that commits regardless of outer transaction

Q: How do you implement soft delete in your application?

Q: What is the purpose of @Query annotation in Spring Data JPA?
A: @Query defines custom JPQL or native SQL queries. Used when derived query methods

A: JPQL is database-agnostic, type-safe. Native SQL for database-specific features or

   serverTimezone=UTC and handling timezone in application layer.

Q: What is the purpose of @JsonFormat in Jackson?
A: @JsonFormat controls JSON serialization/deserialization of dates. Specify pattern, 
   timezone, shape. Used to format dates consistently across API responses and requests.

Q: How do you handle date parsing from API requests?
A: @JsonFormat on DTO fields, or custom deserializer. Validate date format, handle 
   parsing errors gracefully.

Q: How do you implement internationalization (i18n) in Spring Boot?
A: MessageSource bean with properties files for different locales. @Value with 
   locale-specific keys. Accept-Language header from client. LocaleResolver to 
   determine locale. Used for error messages and UI labels.

Q: How do you handle locale-specific date formats?
A: Use Locale-specific date formatters, or send dates in ISO format and let frontend 
   format based on user locale.

Q: What is the purpose of @Validated annotation?
A: @Validated enables method-level validation. Used on service methods to validate 
   parameters. Supports validation groups. Works with Bean Validation annotations like 
   @NotNull, @Size.

Q: How is it different from @Valid?
A: @Valid for method parameters in controllers. @Validated for class-level or 
   method-level validation in any Spring bean.

Q: How do you handle CORS in your application?
A: Spring Security CORS configuration. Allowed origins, methods, headers. 
   CorsConfigurationSource bean. For development, allow all origins. For production, 
   whitelist specific domains.

Q: What security risks with CORS?
A: If misconfigured, can allow unauthorized cross-origin requests. Always validate 
   origin, use HTTPS, avoid credentials with wildcard origins.

Advanced Questions:

Q: How would you scale your application to handle 10x more users?
A: Horizontal scaling—deploy multiple instances behind load balancer. Stateless JWT 
   authentication enables this. Database read replicas for reporting queries. Caching 
   with Redis for frequently accessed data. Database connection pooling optimization. 
   Monitor performance and scale accordingly.

Q: What metrics would you monitor?
A: Response time, throughput, error rate, database connection usage, cache hit ratio, 
   JVM memory and GC.

Q: What is the CAP theorem and how does it relate to your system?
A: CAP theorem states distributed systems can guarantee only two of: Consistency, 
   Availability, Partition tolerance. My system currently uses single database, so 
   CAP doesn't directly apply. If I move to distributed architecture, I'd need to 
   choose—likely CP for financial data consistency.

Q: What would you choose for financial transactions?
A: Consistency and Partition tolerance (CP). Financial data must be consistent, even 
   if temporarily unavailable during network partitions.

Q: How would you implement caching in your application?
A: Spring Cache abstraction with Redis as cache provider. @Cacheable on service methods 
   for expensive operations. @CacheEvict to invalidate on updates. Cache aside 
   pattern—check cache first, if miss, load from database and populate cache. TTL for 
   expiration.

Q: What cache eviction strategy would you use?
A: Time-based expiration (TTL) for most data. Manual eviction on updates for critical 
   data like rate cards. LRU for size-based eviction.

Q: What is the difference between monolithic and microservices architecture?
A: Monolith: single deployable unit, shared database, simpler deployment, easier 
   development. Microservices: independent services, separate databases per service, 
   complex deployment, better scalability. I chose monolith because modules are tightly 
   coupled and complexity doesn't warrant microservices.

Q: When would you move to microservices?
A: When team grows large, modules need independent scaling, different deployment 
   cadences, or technology diversity per service.

Q: How would you convert your monolithic application to microservices?
A: Identify bounded contexts—Farmer Service, Collection Service, Financial Service. 
   Extract each as independent service with own database. Implement inter-service 
   communication via REST or messaging. Use API gateway for routing. Migrate 
   incrementally, starting with least coupled service.

Q: What challenges would you face?
A: Distributed transactions, data consistency across services, network latency, 
   operational complexity, monitoring distributed system.

Q: What is database sharding and how would it apply to your multi-tenant system?
A: Sharding partitions data across multiple database instances. For multi-tenant, shard 
   by tenant—each tenant's data on separate shard. Router determines which shard 
   to query based on tenant ID. Improves scalability for large number of tenants.

Q: What are the challenges of sharding?
A: Cross-shard queries are complex, rebalancing shards is difficult, maintaining 
   referential integrity across shards, operational overhead.

Q: How do you handle distributed transactions across microservices?
A: Saga pattern—sequence of local transactions with compensating actions for rollback. 
   Event-driven architecture with message broker. Event sourcing for audit trail. 
   Two-phase commit for strong consistency (but complex). For financial data, I'd use 
   Saga with eventual consistency.

Q: What is the Saga pattern?
A: Break transaction into sequence of local transactions. If one fails, execute 
   compensating transactions to undo previous steps.

Q: What is the difference between SQL and NoSQL databases?
A: SQL: relational, schema, ACID transactions, complex queries. NoSQL: flexible 
   schema, BASE consistency, horizontal scaling, simple queries. I chose PostgreSQL 
   (SQL) because data is relational, requires ACID for financial transactions, and 
   complex queries are needed.

Q: When would you choose NoSQL?
A: For unstructured data, high write throughput, horizontal scaling requirements, 
   flexible schema, or document/graph data models.

Q: How would you implement read replicas for your PostgreSQL database?
A: Configure PostgreSQL streaming replication. Primary handles writes, replicas handle 
   reads. Application routes read queries to replicas using routing data source or 
   proxy like PgBouncer. Use for reporting and analytics to reduce load on primary.

Q: What is replication lag?
A: Delay between primary and replica sync. Can cause stale reads. Mitigate by monitoring 
   lag, using primary for critical reads, or synchronous replication.

Q: What is the purpose of an API gateway?
A: Single entry point for all API requests. Handles routing, authentication, rate 
   limiting, logging, caching. Simplifies client access—clients call gateway, gateway 
   routes to appropriate service. Provides cross-cutting concerns in one place.

Q: How would you implement rate limiting?
A: Token bucket or leaky bucket algorithm. Track request count per client/IP in Redis. 
   Redis for distributed rate limiting. Return 429 Too Many Requests when limit exceeded.

Q: How would you implement real-time updates in your dashboard?
A: WebSocket for bidirectional communication. Server pushes updates when data changes. 
   Spring WebSocket with STOMP messaging. Client subscribes to topics. Alternative: 
   Server-Sent Events (SSE) for one-way updates. Used for live milk collection updates.

Q: How do you handle WebSocket authentication?
A: Pass JWT token in handshake or query parameter. Validate before establishing 
   connection. Spring Security can integrate with WebSocket.

Q: What is the purpose of message queues and how would you use them?
A: Message queues enable asynchronous processing, decouple services, handle load 
   spikes. I'd use RabbitMQ or Kafka for SMS notifications, report generation, settlement 
   calculations. Producer sends message, consumer processes asynchronously.

Q: What message patterns would you use?
A: Publish-subscribe for notifications (multiple consumers). Point-to-point for task 
   processing (single consumer). Request-reply for synchronous async.

Q: How would you implement audit logging for financial transactions?
A: Event sourcing—store all events as immutable log. Separate read model for queries. 
   Or append-only audit table with before/after values. Trigger-based logging in 
   database. AOP aspects to log service method calls.

Q: What would you log for each transaction?
A: Timestamp, user ID, action, entity ID, before/after values, IP address, request ID 
   for traceability.

Q: How do you handle long-running processes like report generation?
A: Asynchronous processing with message queue. User requests report, system creates 
   job, queues it. Worker process generates report, stores result, notifies user. User 
   polls or receives notification when ready. Alternative: Spring @Async with thread 
   pool.

Q: How do you handle job failures?
A: Retry mechanism with exponential backoff. Dead letter queue for failed jobs. 
   Alerting for manual intervention. Job status tracking.

Q: What is the difference between eager and lazy initialization in Spring?
A: Eager: beans created at startup. Lazy: beans created when first requested. I use 
   lazy for beans not always needed to reduce startup time. @Lazy annotation or 
   default-lazy-init in configuration.

Q: When would you use eager initialization?
A: For beans that must be available at startup, or to fail fast if there are 
   configuration issues.

Q: How do you implement feature flags in your application?
A: Feature toggle library like Togglz or custom implementation. Store feature flags in 
   database or configuration. Check flag in code before executing new feature. Allows 
   gradual rollout, A/B testing, quick rollback.

Q: How do you manage feature flags in production?
A: Admin UI to toggle flags, database for persistence, audit trail for changes, 
   integration with deployment pipeline.

Q: What is the purpose of @Async in Spring?
A: @Async makes method execute asynchronously in separate thread. Used for long-running 
   tasks like sending emails, generating reports. Requires @EnableAsync and task 
   executor configuration. Returns Future or CompletableFuture for result.

Q: How do you handle exceptions in async methods?
A: Exception wrapped in ExecutionException when calling Future.get(). Use 
   CompletableFuture.exceptionally() for error handling.

Q: How would you implement rate limiting for your APIs?
A: Rate limiting library like Resilience4j or Bucket4j. Track request count per 
   user/IP in Redis. Token bucket algorithm. Spring MVC interceptor or filter to check 
   limit before processing request. Return 429 status when exceeded.

Q: What rate limiting strategies would you use?
A: Per-user rate limiting for fairness. Per-IP for abuse prevention. Global rate 
   limiting for overall system protection.

Q: What is the purpose of circuit breaker pattern?
A: Circuit breaker prevents cascading failures. When a service fails repeatedly, 
   circuit opens, calls fail fast. After timeout, circuit closes to retry. Used with 
   Resilience4j. Protects system from downstream failures.

Q: How would you implement it in your application?
A: Annotate external service calls with @CircuitBreaker. Configure failure threshold, 
   timeout, recovery strategies. Fallback method for graceful degradation.

Q: How do you handle database connection leaks?
A: Use connection pooling (HikariCP). Ensure connections are closed—try-with-resources 
   or Spring's @Transactional handles this. Monitor connection pool metrics. Set 
   maximum connection lifetime. Detect leaks with HikariCP leak detection threshold.

Q: What are the symptoms of connection leaks?
A: Connection pool exhaustion, slow performance, timeouts. Monitor active connections 
   vs pool size.

Q: What is the purpose of @Retryable in Spring?
A: @Retryable automatically retries failed method calls. Configurable retry count, 
   backoff strategy. Used for transient failures like network issues. Part of Spring 
   Retry or Resilience4j.

Q: When would you NOT use retry?
A: For non-transient failures (invalid data, authorization errors), operations that are 
   not idempotent, or when retry would worsen the problem.

Q: How would you implement distributed tracing?
A: OpenTelemetry or Spring Cloud Sleuth. Assign trace ID to each request, propagate 
   across service calls. Log trace ID in all logs. Use Jaeger or Zipkin for 
   visualization. Helps debug issues across distributed system.

Q: What information would you include in traces?
A: Trace ID, span ID, parent span ID, service name, operation name, timestamps, 
   error information.

Q: What is the purpose of @Profile in Spring Boot?
A: @Profile activates beans based on active profile. Different configurations for dev, 
   test, production. Use @Profile("dev") on beans or @Value with profile-specific 
   properties. Enables environment-specific behavior.

Q: How do you set active profile?
A: spring.profiles.active property in application.properties, environment variable, or 
   command line argument.

Q: How would you implement blue-green deployment?
A: Two identical production environments. Blue (current), Green (new version). Deploy 
   new version to Green, run smoke tests, switch traffic from Blue to Green. Rollback 
   by switching back. Requires database migration compatibility.

Q: What are the challenges?
A: Database schema changes must be backward compatible, double resource cost during 
   deployment, traffic switching mechanism.

Q: How would you monitor your application in production?
A: Application monitoring with Spring Boot Actuator—health, metrics, info. Logging 
   with ELK stack (Elasticsearch, Logstash, Kibana). APM tool like New Relic or 
   Datadog. Alerting on critical metrics. Distributed tracing for debugging.

Q: What metrics would you track?
A: Response time, error rate, throughput, JVM metrics (memory, GC), database connection 
   pool, cache hit ratio, business metrics (collections per hour).


COMMON MISTAKES TO AVOID IN INTERVIEWS
================================================================================

1. Exaggerating technologies: Don't claim microservices if it's a monolith. Don't 
   claim Redis/Kafka if not implemented. Be honest about what's actually in the 
   project.

2. Memorizing scripts: Speak naturally, don't recite. Understand the concepts 
   deeply so you can explain in your own words.

3. Not knowing the "why": Don't just explain what you built, explain why you made 
   those decisions. Interviewers want to see your reasoning.

4. Ignoring trade-offs: Every technical decision has trade-offs. Acknowledge 
   them—monolith vs microservices, SQL vs NoSQL, caching vs consistency.

5. Overcomplicating answers: Keep answers concise and relevant. Don't go into 
   unnecessary detail unless asked.

6. Not handling follow-ups: Be prepared for deeper questions. If you mention a 
   technology, understand it well enough to answer follow-ups.

7. Blaming tools: Don't say "Spring Security is complicated." Say "I implemented JWT 
   authentication with Spring Security by..."

8. Not mentioning challenges: Interviewers want to hear about problems you faced 
   and how you solved them. It shows problem-solving ability.

9. Ignoring business value: Don't just talk about technology. Explain how your 
   technical decisions serve the business requirements.

10. Being defensive: If you don't know something, admit it. Say "I haven't 
    implemented that yet, but here's how I would approach it."
